WEEK 07

讓 AI 看懂你的世界

用 RAG 把你的資料找出來塞進 prompt，讓 AI 根據事實回答。

  • RAG
  • 向量資料庫
  • LLM Wiki

01本週一句話

RAG 就是先幫 AI 找資料，再請它回答：把最相關的文字塊找出來，一起放進 prompt。

02重點整理

為什麼需要 RAG

Prompt 的第一個重點是「正確的資訊」。與其自己把資料貼給 AI，不如讓電腦自動找出相關資料，這是降低 AI 答錯的好方法。重點在理解原理，不要被新名詞迷惑。

Embedding 模型

把一段文字變成代表它意思的向量。訓練時讓「問題」和「答案」的向量靠近、無關的拉遠（對比學習）。有些模型會在前面加 query: 或 passage: 來區分。

怎麼切文字塊

傳統做法是自動切成每塊 500 字、重疊 50 字。比較新的做法是自己切成想要的樣子，例如法規一條一條切，並加上 metadata：來源網址、日期、分類、作者等。

檢索流程

文件切塊後做成向量資料庫；使用者發問時，問題也轉成向量，找出最接近的幾塊。找到的通常不只一塊，可能需要重新排序（rerank），或補上前後文。

真的需要 RAG 嗎？

模型的上下文越來越長，也可以用 CAG：靠 KV-Cache 把資料全部塞給 LLM。LLM 的「長期記憶」也能用 RAG 做，把過去的對話做成向量資料庫。

LLM Wiki

Karpathy 在 2026 年 4 月分享：把資料放進 raw/，讓 LLM「編譯」成一整套互相連結的 .md wiki，再拿來問答、把輸出歸檔回 wiki、定期健檢。約 100 篇、40 萬字的規模，不一定需要複雜的 RAG。

03核心公式

你的文件→切成文字塊 + metadata→Embedding→向量資料庫
使用者問題→Embedding→找最接近的文字塊→Rerank→放進 prompt 給 LLM

最後組成的 prompt 大概長這樣：

請根據 {retrieved_chunks} 裡的資訊，
      來回應使用者的問題：{question}
做法怎麼給 AI 資料適合
RAG每次只找出最相關的幾段資料量大、需要精準檢索
CAG用 KV-Cache 把全部資料預先存好給 LLM資料量放得進上下文
LLM Wiki讓 LLM 自己整理、維護一套 Markdown 知識庫個人研究、持續累積的主題

課堂範例的 metadata 會寫上標題、資料類型、主管機關、來源網址和整理日期，還附上「檢索練習問題」，方便測試有沒有找對。

04名詞小辭典

RAG（檢索增強生成）
先檢索相關資料，再交給 LLM 生成回答。
Embedding 模型
把文字轉成代表意思的向量的模型。
文字塊（Chunk）
文件切出來、拿來做檢索的一小段文字。
Metadata
文字塊的附加資訊，例如來源、頁數、日期、分類。
向量資料庫
存放大量向量、能快速找出最相近向量的資料庫。
重新排序（Rerank）
把初步找到的結果再依相關程度排一次。
CAG / KV-Cache
把資料的鍵值先算好存起來，整份交給 LLM 使用。
LLM Wiki
由 LLM 撰寫並維護的個人 Markdown 知識庫。

05自我測驗

Q1. RAG 主要在補強 prompt 兩個重點中的哪一個？

「正確的資訊」，讓電腦自動找出相關資料放進 prompt。

Q2. 切文字塊時，為什麼常常讓相鄰的塊重疊？

避免一句重要的話剛好被切斷，造成兩邊都不完整、找不到。

Q3. 什麼情況下可能不需要 RAG？

資料量不大、放得進模型的上下文時，可以直接全部給它（例如 CAG）。Karpathy 的 LLM Wiki 在約百篇文章的規模，也不需要複雜的 RAG。

06我的心得

RAG 聽起來很高深，其實就是「先查資料再回答」，跟我寫報告的流程一樣。

LLM Wiki 讓我想到這個講義網站：把原始資料交給 AI，照固定規則整理成頁面，知識就會一直累積下去。
